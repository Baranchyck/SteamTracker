## 1. Мета

Застосунок майже повністю залежить від зовнішнього Steam Web API, який буває недоступним, повертає приховані дані для приватних профілів і має ліміти запитів. Тому головне завдання тестів — переконатися, що **кожна погана відповідь Steam перетворюється на зрозумілий стан екрана**, а не на падіння застосунку.

Тести пишемо на **xUnit**, підміни залежностей — на **Moq**. Тестовий проєкт — `SteamTracker/SteamTracker.Tests`, папки в ньому повторюють модулі (`Achievements/`, `Matchmaker/`, `SteamApi/`, …).

## 2. Рівні тестування

| Рівень | Що перевіряє | Як ізольовано | Приклади |
|---|---|---|---|
| **Модульні тести сервісів** | Бізнес-логіку шару `Services`: фільтри, сортування, рейтинги, розрахунки, кеш, обмеження паралельних запитів, обробку помилок | `ISteamApiClient`, `IAuthService`, `IStoreClient`, `ILibraryService` підмінюються через `Mock<…>`; мережі немає | `LibraryServiceTests`, `AchievementServiceTests`, `ComparisonServiceTests`, `PriceAnalyzerServiceTests`, `MatchmakerServiceTests` |
| **Тести HTTP-клієнтів** | Розбір справжніх JSON-відповідей Steam, URL запитів, пачки (100 SteamID / 50 appid), коди помилок і таймаути | Підмінений `HttpMessageHandler` (`RecordingHandler`, `ThrowingHandler` у `SteamApi/TestHttpHandlers.cs`) замість мережі | `SteamApiClientTests`, `SteamApiClientFriendsTests`, `SteamApiClientAchievementsTests`, `StoreClientTests` |
| **Інтеграційні тести даних** | Репозиторії й ініціалізацію схеми на **справжній SQLite**: збереження, оновлення без дублікатів, міграцію наявної БД | Тимчасовий файл БД (`DataAccess/TempSqliteDatabase.cs`), видаляється після тесту. In-memory БД не підходить: фабрика відкриває нове з'єднання на кожен виклик | `SqliteUserRepositoryTests`, `SqliteSettingsRepositoryTests`, `DatabaseInitializerTests` |
| **Тести входу через Steam OpenID** | Перевірку відповіді OpenID і локальний `HttpListener` для callback | Слухач піднімається лише на `localhost`, справжній Steam не викликається | `SteamOpenIdValidatorTests`, `SteamOpenIdVerifierTests`, `LocalCallbackListenerTests` |
| **Ручна перевірка UI на фейках** | Вигляд екранів за макетом Figma і всі стани: дані, порожньо, помилка, приватний профіль | `"UseFakes": true` в `appsettings.json`; у Debug на кожному екрані є перемикач станів фейкового сервісу | Екрани «Бібліотека», «Друзі-радар», «Час гри з друзями», «Досягнення», «Co-op Matchmaker» |
| **Ручна перевірка зі справжнім акаунтом** | Що екран показує реальні дані зі Steam | `"UseFakes": false` і власний API-ключ; робить автор PR перед рев'ю | Скріншоти «реальні дані» в описі PR |

### Перехресна перевірка

Після того як сервіс написано, інший учасник читає його код і тести й дописує тести на випадки, яких автор не передбачив. Знайдені баги не виправляються мовчки, а заводяться окремим issue на автора. Тест, що ловить баг, позначається `[Fact(Skip = "Баг #N: …")]`, щоб CI лишався зеленим, і розблоковується після виправлення.

Приклад: перевірка `AchievementService` і `MatchmakerService` (#98) знайшла баг #124 — переповнення `int` у `BuildRoadmap`.

## 3. Що свідомо не тестуємо автоматично

| Що | Чому | Чим компенсуємо |
|---|---|---|
| **Вікна й екрани WPF** (`SteamTracker.UI`) | UI-автотести для WPF крихкі й повільні, а логіки в екранах мало: вона в сервісах, які покриті тестами | Ручна перевірка на фейкових сервісах з перемикачем станів + скріншоти в PR |
| **Справжній Steam Web API у CI** | У CI немає API-ключа (його не можна комітити), Steam буває недоступний, а ліміти запитів зробили б тести нестабільними | Тести клієнтів на записаних відповідях Steam; ручна перевірка зі справжнім акаунтом перед мерджем |
| **Неофіційний Store API (`appdetails`)** | Без SLA, ліміт ~200 запитів / 5 хв | Клієнт розрахований на збої (часткові дані, фолбек «лише час гри») і це покрито тестами |
| **Справжній вхід через браузер** | Потребує ручного логіну в Steam | Тести валідації OpenID-відповіді + ручний вхід |

## 4. Обов'язкові крайові ситуації

Кожен новий сервіс або клієнт має тести на ситуації нижче (ті, що стосуються саме його):

| Ситуація | Очікувана поведінка | Де вже покрито |
|---|---|---|
| **Приватний профіль / прихована бібліотека / прихований список друзів** | Статус `Private` з підказкою, як відкрити, а не `Error` і не «0 годин» | Library, Achievements, FriendsRadar, Comparison, Matchmaker |
| **Порожні дані** (немає ігор, друзів, ачівок) | `Available` з порожнім списком — це не помилка | FriendsRadar, Comparison, Achievements, Matchmaker, StoreClient |
| **0 хвилин гри** | Жодного ділення на нуль; гра не потрапляє в розрахунки, де час — дільник | PriceAnalyzer, Comparison |
| **HTTP 400 / 401 / 403** | `401` на списку друзів → `null` (список прихований); `403` «Profile is not public» на ачівках → `null` (статистика прихована); `403` на друзях (невалідний ключ) і `400` → `SteamApiException` | SteamApiClient (друзі, ачівки) |
| **HTTP 429 (ліміт запитів)** | Зупинити дозавантаження й повернути те, що вже отримано | StoreClient |
| **Таймаут і мережеві помилки** | `SteamApiException` у клієнті → `Error` з людським повідомленням у сервісі; Store — порожній результат без винятку | SteamApiClient, StoreClient, усі сервіси (`SteamApiException → Error`) |
| **Битий JSON** | Те саме, що мережева помилка | SteamApiClient, StoreClient |
| **Скасування (`CancellationToken`)** | `OperationCanceledException`, нові запити не стартують | Achievements (#98) |
| **Межі вводу** (0, максимум, «максимум + 1», пробіли, дублікати) | Межа включно працює, за межею — зрозуміла помилка без запитів у Steam | Matchmaker, SteamIdResolver, Achievements (#98) |
| **Немає залогіненого користувача** | `Error` без жодного запиту в Steam | Усі сервіси |

Повідомлення для користувача не повинні містити технічних деталей винятку (тести перевіряють `Assert.DoesNotContain("boom", result.Message)`).

## 5. Правила команди

1. **Кожна таска з кодом має розділ «Тести»** з переліком сценаріїв, які треба покрити. PR закриває таску лише разом із цими тестами.
2. **PR без зелених тестів не мерджиться.** CI запускається на кожен PR у `main`, а правило гілки `main` вимагає зелений CI й approve рев'юера.
3. **Тести не ходять у мережу й не потребують API-ключа** — інакше вони впадуть у CI. Steam підмінюється моками або `HttpMessageHandler`.
4. **Контракт — окремим PR першим**, щоб фронтенд і тести могли спиратися на інтерфейс, поки пишеться реалізація.
5. **Знайдений баг — окремий issue на автора** + тест зі `Skip = "Баг #N"`, а не тихе виправлення в чужому коді.
6. **Фейковий сервіс повторює правила справжнього** (сортування, фільтри, статуси), щоб ручна перевірка UI на фейках відповідала реальній поведінці.

## 6. Як запускати тести

Усі тести (з кореня репозиторію):

```bash
dotnet test SteamTracker/SteamTracker.sln
```

Лише тести одного модуля — фільтр за назвою класу:

```bash
dotnet test SteamTracker/SteamTracker.sln --filter "FullyQualifiedName~Matchmaker"
```

Так само, як у CI (Release):

```bash
dotnet test SteamTracker/SteamTracker.sln -c Release
```

**У Visual Studio:** Test → Test Explorer → Run All.

**Де дивитись результати CI:**
- у кожному PR — перевірка **CI / build-and-test** внизу сторінки; червона перевірка блокує Merge;
- усі запуски — вкладка [Actions](https://github.com/Baranchyck/SteamTracker/actions/workflows/ci.yml) репозиторію; у лозі кроку **Test** видно кожен тест і причину падіння;
- статус `main` — бейдж CI на початку [README](../README.md).

Workflow: [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) — `windows-latest` (WPF не збирається на Linux), `restore` → `build -c Release` → `test`.
